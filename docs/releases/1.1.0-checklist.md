# Releasing 1.1.0

The Phase 2 release. **The tag has not been pushed** — this page is the
sequence, written so the tag is a decision somebody makes rather than a command
they reconstruct from the workflow file. Boxes ticked below were done on
2026-09-22, with what was checked stated beside them.

The automation in [`release.yml`](../../.github/workflows/release.yml) does the
building. It triggers on a `v*` tag and nothing else, so everything below is
either a check before the tag or a verification after it.

> **1.1.0 is the stable tag, and that is what makes it different from
> `1.1.0-beta.1`.** [COMPATIBILITY.md](../api/COMPATIBILITY.md) §1 attaches the
> `/api/v1` freeze at the first stable tag. Once this is pushed, the reporting
> operations — `report-templates`, `report-schedules`, `report-runs`, artifacts,
> share links, brand profiles, `expiries` — can only be changed compatibly.
> Anything about their shape that is still uncomfortable has to be settled
> before, not after.

## The tag

```bash
git checkout main && git pull
git tag -a v1.1.0 -m "v1.1.0 — reporting"
git push origin v1.1.0
```

That push is the irreversible step. Images are pulled by tag and by digest, and
a `1.1.0` that somebody has already pulled cannot be replaced — only superseded
by `1.1.1`.

## After the tag

- [ ] **Watch `release.yml` to completion.** It produces the binaries, the
      checksums, the SBOM and the multi-arch images, and pushes to both GHCR and
      Docker Hub. A failure part-way leaves a tag with some artefacts and not
      others, which is worse than no tag.
- [ ] **Verify the binary reports the right version**, because the whole point of
      the ldflags is that it does:
      ```bash
      docker run --rm ghcr.io/webloomlabs/uptime-cairn:1.1.0 -version
      ```
- [ ] **Verify the checksums** against the release assets, from a machine that
      did not build them.
- [ ] **Verify `docker run webloomlabs/uptime-cairn` resolves**, because that is
      the command in `README.md` and the one people actually type. Publishing to
      GHCR and documenting Docker Hub is how a quick start stops working.
- [ ] **Upgrade a real install from `1.1.0-beta.1`** and confirm migrations `0008`
      and `0009` are already applied and nothing re-runs. (No migration was added
      after the beta — `0009_artifact_mirror.sql` is still the latest — so
      nothing new should run.)
- [ ] **Replace the generated release notes.** `release.yml` publishes GitHub's
      auto-generated list of PR titles; swap in the short notes:
      ```bash
      gh release edit v1.1.0 --notes-file docs/releases/1.1.0-notes.md
      ```
- [ ] **Post the announcement.**
- [ ] **Tick the release box** in [PHASE-2-TODO.md](../plans/PHASE-2-TODO.md), and
      the buffer box with it — the buffer is spent when the phase ships.

## If it goes wrong

Do not delete or move the tag. Fix forward with `1.1.1`. A moved tag is a
different set of bytes under a name somebody has already recorded in a
`docker-compose.yml`, and that is a worse failure than a bad release, because
nothing about it is visible from the outside.
