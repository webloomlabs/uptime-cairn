## Uptime Cairn 1.1.0 — reporting

Uptime Cairn is an open source uptime monitoring platform that runs as a single
binary for one person with three sites, and as a control plane with remote probes
for an install with five thousand monitors. Same codebase, same features, no
paywalled tier.

**1.1.0 adds reporting**, and it is the release that makes the tool useful to
somebody who has to show their uptime to another person — a client, an auditor,
a manager who wants the month in writing.

### What you can do now

**Define a report and have it arrive without being at a keyboard.** A report
template says what it covers — monitors, groups, or a tag that resolves at run
time, so adding a monitor to a client's tag puts it in that client's next report
without editing anything. A schedule fires it monthly, weekly, on a cron
expression if the enumeration does not fit. Delivery goes to email, Slack, a
webhook, or a drop in an S3 bucket.

**Five report types**, because "a report" is not one thing. An **SLA/SLO** report
carries target against actual, the error budget consumed and remaining, the burn
rate, and a breach log with timestamps. An **uptime summary** is the default and
deliberately carries no SLO vocabulary at all, even where the monitors have
targets — an agency does not publish the internal target it set on a client's
monitors. An **incident post-mortem** draws MTTD/MTTA/MTTR from the incident
record. A **comparative** report puts a period beside the one before it, or a
monitor beside a monitor. And a **custom** builder chooses the blocks and their
order.

**Four formats from one model.** PDF, HTML, CSV and JSON are siblings — the PDF
is never a converted web page. Rendering is pure Go and in-process: no headless
browser, no sidecar, nothing to install alongside the binary.

**The figures state how they were produced.** Every report prints its
denominator and its maintenance policy on its face, and says which rollup tier
answered it. A percentage whose method can be switched off is a percentage the
person holding it cannot check, which defeats the point of handing it to them.

**White-labelling.** A brand profile puts a client's name, colour and logo on the
report, copied onto each artifact as it runs — so rebranding in June does not
change what January's report says it said.

**Share links.** A revocable, optionally expiring URL onto a stored report, for
the client who will not create an account. It serves the artifact that was filed,
never a re-render, so the figures somebody bookmarked do not move.

**A certificate and domain expiry calendar**, both as a screen and as a report
section: what runs out in the next ninety days, soonest first, with anything
already lapsed at the top.

**History you can actually browse.** Any past range at the best resolution
retention holds, always labelled with the resolution actually used — and told
plainly when a range reaches back further than the install has been running.

### Upgrading

From `1.0.1` or `1.1.0-beta.1`: replace the binary or the image. Migrations run
at start-up. Reports are written to `<data-dir>/reports/`, which **must be in
your backup alongside the database** — take the database first, then the
directory. See the [backup and restore guide](../operations/backup-restore.md).

### `/api/v1` is frozen at this tag

Per [COMPATIBILITY.md](../api/COMPATIBILITY.md), the stable tag attaches the
compatibility promise to the reporting operations. They can change compatibly
from here and not otherwise.
